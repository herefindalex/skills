# Conditional follow-up

Read only the relevant row. These are decision prompts, not required mechanisms or a test checklist.

| Trigger in the commissioned task | Distinction worth checking |
|---|---|
| Async completion or recovery | Which acceptance/effect/identity facts can the real client recover? Keep internal outcome verification out of the client driver's capabilities. A response alone may not establish effects. |
| Multi-call workflow | Which relationship must hold across calls? Check the stated completeness, identity, or consistency promise while allowing valid ordering and page boundaries. |
| Time-limited protection | What begins/ends protection, and what can erase its supporting information? Examine only schedules relevant to the agreed window. Presence of a key or TTL is not its full semantics. |
| A changed read path or version | Which premises of old evidence still hold? Retain the historical result in its old scope; identify the uncovered new path without rewriting history. |
| Explicit repair review | Does the original counterexample disappear while lawful client behavior remains? Distinguish restoration, contract narrowing, and temporary mitigation. Include old state/workers only if restoring their promise is within the commission. |

When evidence is indirect, state why it transfers to the target. A toy model remains a model; a selected schedule remains that schedule; a process interruption does not establish power-loss behavior. Preserve a useful narrow result even when stronger claims remain untested.

Before another probe, write the possible outcome that would change the current judgment or next action. If none exists, finish the review.
